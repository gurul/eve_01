## Differences
- Everything that calls out is async (`ConnectTokenSource::get`/`refresh`/`hold`, the bridge's `try_start`, `execute`, `connect_link`, `connections`, `close`); the Python was blocking on threads. `start()` spawns a tokio task on the caller's runtime where Python started a daemon thread, and a thread with a runtime of its own when called outside one. `close()` waits up to 2 s for the task, then aborts it (Python joins for 2 s and closes the HTTP clients, which ends a request in flight), and closes the three sessions' connections: a later call sends nothing and fails with httpx's closed-client RuntimeError (`Cannot send a request, as the client has been closed.`), as in Python.
- Python catches any exception inside the token source and the bridge and logs its type. The Rust code has no exceptions to catch on those paths; the two reader seams (`Readers`) are run under `catch_unwind`, and a panic there is logged as `panic` where Python logs the exception's class.
- A reqwest failure after the connection was made that is not a timeout reads as `RemoteProtocolError`, so the model is told the call may have run (httpx would name a write failure `WriteError`, without that note).
- Upstream edit: eve-brain's `onboarding::TOKEN_SHAPE`, `answer`, `oauth_word` and `expires_at` were `pub(crate)`; they are `pub` now so this crate reads the token endpoint's answer with onboarding's own readers, as the Python imports `_TOKEN_SHAPE`, `_answer`, `_oauth_word` and `_expires_at` from onboarding. eve-brain has no PARITY.md yet to record it in.
